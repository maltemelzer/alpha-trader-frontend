# Alpha-Trader – alternatives Frontend („Bankiersgrün“)

Inoffizielles Web-Frontend für die Börsensimulation [Alpha-Trader](https://alpha-trader.com): Spieler gründen Unternehmen, handeln Aktien, Anleihen, Coins, Fonds, Immobilien; Kurse entstehen nur aus Spielerhandel. Sprache der Oberfläche: Deutsch.

## Grundsätze (wichtiger als alles andere)
1. **Visualisieren statt beschreiben.** Jede Zahl, die eine Entwicklung, Verteilung oder einen Vergleich hat, wird als Diagramm, Balken, Sparkline, Heatmap oder Fortschrittsbalken gezeigt – nicht als Absatz oder lange Tabelle. Text nur für Namen, Labels, Tooltips. Welches Diagramm wofür: siehe Design-System `guidelines/diagramme.md`.
2. **Eine Seite = ein Bildschirm.** Ziel-Viewports 1440×900 und 1280×720 (Desktop), 390×844 (Handy): Hauptseiten passen ohne Seiten-Scroll. Mittel: Layout mit `100dvh`-Grid, Panels mit fester Höhe und internem Scroll (Orderbuch, Trades), Tabs/Segmente statt Untereinanderstapeln, Kennzahlen als kompakte `StatTile`-Reihe, Details in Tooltip/Sheet/Dialog. Wenn eine Seite doch scrollen muss, steht das Wichtigste above the fold – und das wird in der PR begründet.
3. **Mobil gleichwertig.** Alles ab 360 px Breite; `BottomNav` < 720 px; Handel über `TradeBar` + `Sheet`; Tippflächen ≥ 44 px; nichts nur per Hover.
4. **Handy (< 720 px):** Über dem Inhalt höchstens eine Meta-Zeile + **eine** Steuerzeile (+ optional eine Kennzahlenzeile `MiniStats`); der Inhalt bekommt ≥ 60 % der Höhe. Zeitraum/Sortierung/Filter ins Sheet hinter `OptionsButton` oder in den Kartenkopf, nie als eigene Zeile. Höchstens 4 Segmente, mehr Ansichten als `ScrollTabs` (Randverlauf, ☰-Sheet) oder `ViewPicker`. Jede Desktop-Funktion hat am Handy einen Ort; Hauptaktionen unten in der Daumenzone. Bausteine in `src/app/phone.tsx` (`MiniStats`, `OptionsButton`, `Option`, `ScrollTabs`, `ViewPicker`, `ViewList`, `PhoneProfile`, `useEdgeFade`; CSS `.ph-bar`, `.ph-btn`, `.ph-sheet`) – keine eigenen Varianten bauen.
5. **Navigation in drei Ebenen – auf jeder Seite gleich.** (1) *Seite*: Kopf/BottomNav. (2) *Ansicht* `?ansicht=`: **eine** Reiterleiste direkt unter dem Seitentitel; jede Ansicht legt fest, welche Karten zu sehen sind (breit: Haupt- + Kontextkarte). (3) *Filter* (`zeitraum`, `art` = Anlageklasse, `konto`, `suche` …): gelten für die **ganze Seite** und stehen rechts in derselben Zeile – bis zwei als Segmente, bei mehr nur die `primary` und der Rest hinter „Filter (n)“, Abweichungen als Chips mit ✕. Ein Filter, der nur für manche Ansichten gilt, wird in den anderen ausgeblendet (`views`). Karten haben **nie Reiter**; ein Kartenkopf darf höchstens die Darstellung **dieser** Karte umschalten (Segmente in `Card action`, z. B. Orderbuch|Tiefe|Trades) – nie eine andere Karte. Handy: Steuerzeile `[Ansichten (ScrollTabs, ☰ ab 5) | Filterknopf mit Zähler]`, Filter im Sheet, gewählte Filter in der Meta-Zeile (`filterSummary`); eine Kontextkarte wird dort eine eigene Ansicht mit `parent` (breit zeigt derselbe Link die Eltern-Ansicht). Zeiträume nur aus `RANGE_VOCAB` (`src/lib/ranges.ts`). Umsetzung: `usePageView`, `useFilters`, `PageNav` (`src/app/pagenav.tsx`, reine Logik + Tests in `src/lib/pagenav.ts`); `npm run audit` meldet unter `nav` Seiten mit mehreren Reiterleisten oder Reitern in Karten. Umgestellt: Zentralbank, Geldflüsse – übrige Seiten folgen (Zuordnung im Plan „Einheitliches Navigations- und Filterkonzept“).
6. **Design-System vor Eigenbau.** Erst Komponente aus `Bankiersgruen` suchen (`index.d.ts`), dann kombinieren, erst zuletzt neu bauen – und neue Muster als Vorschlag fürs Design-System notieren.

## Stack
- Vite + React 18 + TypeScript 5 (strict), reine SPA, kein eigener Server.
- **React bleibt auf 18**, weil das Design-System-Bundle für React 18 gebaut ist. Deshalb React Router 7 (Version 8 verlangt React 19), `@types/react@18`. TypeScript bleibt auf 5.x (openapi-typescript und typescript-eslint unterstützen 7 noch nicht).
- React Router (Routen = Spielbereiche), TanStack Query für alle API-Daten (Caching, Polling für Kurse).
- API-Typen generiert aus der OpenAPI-Spec (`src/api/schema.d.ts`, nicht von Hand ändern), Client in `src/api/client.ts` (`openapi-fetch`, Auth-Middleware, `login()`, `unwrap()`). View-Typen in `src/api/types.ts`: Aliase auf das Schema; nur wo die Spec bloß `object` liefert (Listing-Profil, Orderbuch, Portfolio), eine knappe Form nach echten Antworten.
- Alle Abfragen als Hooks in `src/api/queries.ts` (ein Hook je Endpunkt, Polling: Kurse/Orderbuch 15 s, Rest 60 s). Spring-`Pageable` flach senden (`?page=0&size=50&sort=date,desc`) – dafür `pageableSerializer`.
- Diagramme: Plotly 3.x (`plotly.js-dist-min`) – keine zweite Chart-Bibliothek. Immer über `<Plot figure={(theme, width) => …} />` aus `src/charts/Plot.tsx`: lädt Plotly erst bei Bedarf, füllt seinen Container, zeichnet bei Größen- und Theme-Wechsel neu. Figuren als reine Funktionen (Beispiel `src/security/charts.ts`), Achsen-Kurzformen mit `short()` aus `src/lib/format.ts`.
- Tests: Vitest + Testing Library; Formatierungsfunktionen (Beträge, Kurse, Datum) immer getestet.

## API
- Spec: https://stable.alpha-trader.com/v3/api-docs (Swagger UI: https://stable.alpha-trader.com/swagger-ui/index.html). Server: `stable` (Standard), `nightly`, `dev`.
- CORS ist offen (Origin wird gespiegelt) – kein Proxy nötig.
- Login: `POST /user/token?username=…&password=…&partnerId=…` → Antwort `{ code, message, … }`, das JWT steht in `message`.
- Authentifizierte Requests: `Authorization: Bearer <JWT>` (verifiziert). `X-Authorization` ist **nicht** der Token-Header, darüber kann die Partner-ID mitgeschickt werden. Token im `sessionStorage` des Tabs (`at.token`), nie loggen. Neue Tabs holen ihn per `BroadcastChannel('at.auth')` von offenen Tabs (`requestTokenFromOtherTabs`, `RequireAuth` wartet solange mit `checking`), Abmelden meldet alle Tabs ab. „Angemeldet bleiben“ legt ihn zusätzlich 30 Tage in `localStorage` (`at.remember`) – das JWT hat selbst kein `exp`. Kein Cookie: die API liegt auf einer anderen Domain und will `Authorization: Bearer`.
- `PARTNER_ID` ist öffentlich und kommt als `VITE_PARTNER_ID` in den Build; Basis-URL als `VITE_API_BASE`.
- Neuere Endpunkte unter `/api/v2/...` bevorzugen, wenn es beide gibt. Zeitstempel sind Millisekunden.
- Wichtige Endpunkte je Seite stehen in den READMEs der Seitenvorlagen im Design-System (z. B. Wertpapierseite: `/listingprofiles/{asin}`, `/pricespreads/{asin}`, `/orderbook/{asin}`, `/shareholders/{asin}`, `/v2/securityorderlogs/by-asin/{asin}`, `/v2/historizedlistingdata/{asin}`).

## Testen gegen die echte API (für Claude)
- Zugangsdaten in `.env` (`AT_USERNAME`, `AT_PASSWORD`, `PARTNER_ID`; nie committen, nie ausgeben – auch Tokens nicht in Tool-Ausgaben drucken). Claude darf sich damit einloggen, um Antwortformen zu prüfen und Seiten im Browser zu verifizieren. Dafür `npm run api:get -- /api/…` benutzen (kann nur GET).
- `stable` ist das Live-Spiel: **nur lesende Requests ohne Rückfrage.** Alles Schreibende (Orders, Überweisungen, Kapitalmaßnahmen, Chat, Abstimmungen …) nur nach ausdrücklicher Bestätigung.
- Browser: Claude in Chrome ist verbunden (`/chrome`, Desktop-App vorher beenden, sonst belegt sie die Erweiterung). Der Nutzer meldet sich im Claude-Tab selbst an (Token im sessionStorage des Tabs). Handy-Größe weiter mit `npm run shot`.
- UI-Änderungen mit `npm run shot` prüfen (1440×900, 1280×720, 390×844): passt die Seite ohne Scrollen? Stimmen Farben im Farbenblind-Modus? Ansichten stehen in der URL (z. B. `/wertpapier/STSN3G03LB?markt=depth&zeitraum=K`), so lässt sich jede Ansicht direkt fotografieren.

## Aufbau der App
- `src/app/` Rahmen: `AppShell` (AppHeader mit Chat-Knopf + Glocke `Notifications.tsx`, unter 720 px BottomNav), Bereiche in `nav.ts`. **Handy-Navigation:** Der Kopf zeigt statt der Wortmarke den Seitennamen mit ▾ (`titleOf`), Tippen öffnet das Sheet „Alle Seiten“ (`SiteMap.tsx`, alle Seiten aller Bereiche, aktueller Bereich oben) – ebenso „Mehr“ und ein zweiter Tipp auf den aktiven Tab. Tabs merken sich die zuletzt besuchte Unterseite je Bereich (sessionStorage `at.lastPage`). Der eigene `PageHeader`-Titel ist am Handy nur für Screenreader da (eyebrow/description aus), das Börsenband fehlt am Handy. Die DS-Tippfläche `::before` der Wortmarke ist dort abgeschaltet, sie fing den Tipp auf den Titelknopf ab. Seite = Grid in `100dvh`, `main` scrollt nur im Notfall.
- **Ungelesene Nachrichten** überall: Zahl ungelesener Nachrichten (Direkt + Gruppen, `useChatUnread()`, Lobbys zählen nie) am Chat-Knopf im Kopf (`NotificationBell icon="chat"`, auch am Handy), an „Community“/„Nachrichten“ in Kopf und BottomNav und im Tab-Titel „(3) Alpha-Trader“ (`titleWithUnread`). Live: `ChatLive` (in der Shell) abonniert `/user/topic/chatmessages/{id}` **aller** Nicht-Lobby-Chats – neue fremde Nachricht → sofort +1 (`applyIncoming`, zählt jede Nachricht einmal, eigene über den Namen) und ein Hinweis-Toast mit „Öffnen“, außer auf `/nachrichten` oder bei offener Leiste; Push auf `/user/topic/my/chats` → Liste 1,5 s später neu laden (ob dessen `numOfUnreadMessages` die Sicht des Empfängers ist, ist unbestätigt). Lesen (`PUT …/chats/read`) setzt die Zahl auf 0.
- **Wertpapiere im Chat:** `#ASIN` verlinkt, `!ASIN` hängt zusätzlich eine Karte an (`AssetEmbed.tsx` → DS `AssetCard`: Kurs, Veränderung 24 h, Sparkline 30 T aus `recentPrices`, Geld/Brief + Zins/Börsenwert/Spread; Daten `listingprofiles` + `historizedlistingdata`, gleicher Cache wie die Wertpapierseite), alte `$ASIN` bleiben Links. `#`/`!` brauchen die volle ASIN (10 Zeichen) und kein Wortzeichen davor („#1“, „Super!“ bleiben Text) – dieselbe Regel in `src/chat/mentions.ts` (getestet) und in `renderChatText`/`chatEmbeds` des DS. Höchstens drei Karten je Nachricht; Karten am Anfang/Ende stehen nicht noch einmal in der Blase, eine Nachricht nur aus Karten hat keine Blase. Beim Tippen von `#`/`!` schlägt `useMentions` (Suche `pricespreads?search=`, ab 2 Zeichen – ohne Anleihen/Repos) Wertpapiere vor: DS `MentionMenu` im `popup` des `ChatComposer`, ↑↓/Enter/Tab/Esc über dessen `onKeyDown`, der Cursor wird aus dem Textfeld gelesen (`activeTrigger`, `applyMention`). Namen für den Tooltip der Links über `useListings`. Ohne `.env` im Container mit abgefangener API (puppeteer `setRequestInterception`) fotografiert, nicht gegen den Server gesendet.
- **Chat-Leiste** (`src/chat/ChatSidebar.tsx`): ab 1200 px Viewport rechts angedockt (340 px, Spalte der Shell `.shell--chat`, unter dem Kopf bis unten), Chat-Knopf oder Taste „C“ schaltet, Zustand in localStorage (`at.chatSidebar`), zu = keine Spalte. Nicht auf `/nachrichten` (dort der Vollbild-Chat), nicht unter 1200 px (Knopf führt dann zu `/nachrichten`). Liste → Chat → zurück, „Vollbild“ → `/nachrichten/:id`, Senden-Knopf umrandet (die Seite hat ihren Messing-Knopf), ohne „Verlassen“. Chatseite und Leiste teilen `ChatPanel` (die `ChatWindow` wechselt per Container Query nach eigener Breite). **Seitenbreiten:** Mit angedockter Leiste verschiebt `useMediaQuery` alle `min-/max-width`-Schwellen um 340 px (`setLayoutInset`/`primeLayoutInset`, `shiftQuery`) – Seiten entscheiden nach ihrer Spalte (1440 → 1100 px = breit, 1280 → 940 px = mittleres Layout). CSS-Media-Queries können das nicht: Breiten-Regeln, die die Spalte meinen, brauchen eine Kopie `@media (max-width: <N+340>px) { .shell--chat … }` (so in `CompanyPage.css`, `SponsoringPage.css`; Forum/Quote bei 899 px fehlen noch, greifen erst unter 1240 px Viewport).
- Börsenband (`src/app/MarketTape.tsx`, Rechnen in `tape.ts`): unter dem Kopf auf allen Seiten (außer Handy-Wertpapierseite). Trades laufen langsam (32 px/s) von rechts nach links, je Trade ▲/▼ gegen den vorigen Trade desselben Papiers. Daten: `useRecentTrades()` fragt `/api/securityorderlogs?startDate=` nur seit dem neuesten bekannten Trade ab (statt 1.000 Trades je Abruf), Namen einzeln über `useListings()` (`/api/listings/{asin}`, für die Sitzung gecacht). Es gibt mehr Trades, als ein ruhiges Band zeigen kann: nur die neuesten 12 warten. Hover/Fokus hält an, „Live“-Knopf pausiert dauerhaft (localStorage), bei `prefers-reduced-motion` stehen die neuesten Trades still. Trades zum Preis 0 (Übertragungen) fehlen. Gegen Ruckler: Namen werden vorab geladen, ein Trade läuft erst ein, wenn sein Name da ist (max. 3 s, sonst mit ASIN) – ein später Name macht ein sichtbares Element breiter; Breiten mit `getBoundingClientRect` (nicht gerundetes `offsetWidth`); der Zähler „Trades/min“ hat feste Breite, sonst schiebt er das Band alle 15 s. Die Shell-Spalte ist `minmax(0, 1fr)`, sonst macht das Band alle Seiten breit.
- Aufleuchten bei Änderung: `useTick(wert)` + `tickClass()` aus `src/lib/useTick.ts` färbt einen Wert 1,6 s in `--gain-tint`/`--loss-tint` (CSS `.tick--up/down` in `layout.css`). Genutzt für Depotwert im Kopf und den letzten Kurs im `SecurityHeader` (`.tick-price--up/down` greift auf `.bnk-sech__price`).
- `src/app/layout.css` gemeinsames Ein-Bildschirm-Layout: `.page` (Kopf + Rest), `.page__body`/`.page__col` (Grids), `.panel` + `.panel__fill` (Karte füllt Zelle, Inhalt scrollt), `.panel__tabs` (Tabs in füllender Karte, Panel scrollt). Neu im DS: `Card fill` – für neue Seiten bevorzugen.
- Seiten (je Ordner `XyzPage.tsx`, `derive.ts` + Test, ggf. `charts.ts`): `organisation/` (Startseite „Meine Organisation“; Reiter „Indizes“ = eigene Indizes `MyIndexes`: `?rechts=indizes` breit, `?ansicht=indizes` Handy; Reiter `?ansicht=performance` in `PerformancePanel.tsx`, Rechnen in `performance.ts`: `?gv=offen` Buchgewinn je Position als divergierende Balken (größte 10 + „Übrige“, ein Ausreißer > 3× des Zweiten wird gekürzt) · `?gv=realisiert&zeitraum=7T|30T|alle` `TradeStats` + beste/schlechteste 5 Verkäufe · `?konto=<Wertpapierkonto>` Firmenkonto, auswählbar für CEOs; breit ersetzt der Reiter die Karte „Privatportfolio“), `orders/`, `market/` (Screener, Marktkarte – siehe Stolperfallen „Markt“), `highscores/`, `chat/` (`/nachrichten/:chatId?`, gemeinsamer Inhalt `ChatPanel.tsx`, Leiste `ChatSidebar.tsx`, Live/Ungelesen `ChatLive.tsx` + `unread.ts`; Gruppen: Inhaber/Stellvertretung benennen um und entfernen Mitglieder im Mitglieder-Sheet), `news/` (`/zeitung/:postId?`, Suche `?suche=`), `players/` (`/spieler/:username`), `sponsoring/` (`/sponsoring?ansicht=features|kosten|erreicht|sponsoren`), `alliances/` (`/allianzen` mit `?gruenden=1`, `/allianz/:id` mit Verlassen, `?bearbeiten=1`, `?aufnehmen=1`; Die Emission liegt als ein Brief zum Ausgabepreis P im Buch (≈ 1,01 × Bezugsverhältnis R × Referenzkurs, vom Emittenten gerundet), Laufzeit 24 h, Cap = Referenzkurs × 1,1 (Call) bzw. × 0,9 (Put). Geldfluss: Emittent → Treuhand „Warrant Deposit“ bei Ausgabe; der **Kaufpreis geht auch in die Treuhand**, nicht an den Emittenten; bei Fälligkeit zahlt die Treuhand den Inhabern „Repurchase of # (#): # warrants“ und dem Emittenten den Rest als „Warrant refund“ (kauft niemand: volle Hinterlegung zurück).
    - **Call:** Auszahlung = R × min(Kurs bei Fälligkeit, Cap), **auf den Cent abgerundet** – der volle Wert, nicht die Differenz zum Referenzkurs. Beleg: Konto „Malte“ kaufte WAS6HHKLOM (Seylor Tender Bank CALL 1,62, R 0,1, Cap 1,782) am 25.09. 23:11 komplett: 349.370.331 × 0,17 € = 59.392.956,27 €; Fälligkeit 26.09. 10:13:55, letzter Trade des Basiswerts 10:13:35 zu 1,66 € → 0,16 € je Schein = 55.899.252,96 €, Emittent bekam 6.358.540,03 € (= Hinterlegung 2.864.836,72 + 0,01 je Schein); die Treuhand geht auf den Cent auf. Hinterlegung = R × Cap − P bei allen 9 geprüften Calls (Topf = R × Cap je Schein).
    - **Put:** Hinterlegung = P − R × Cap bei allen 8 geprüften Puts, also Topf = 2P − R × Cap je Schein → Auszahlung = 2P − R × max(Kurs, Cap), mindestens 0 (spiegelbildlich um P). **Aus Hinterlegungen abgeleitet, keine Put-Einlösung gesehen.** P ist im UI der Brief (`termsOf(w, ask)`), ohne Brief R × Referenzkurs.
    - Folge: ein Schein ist eine gedeckelte 1:1-Wette, kein Hebel. Zum Ausgabepreis gewinnt ein Call über P/R (≈ Referenzkurs + 1 %), höchstens ~+5 … +9 % am Cap; ein Put unter P/R, höchstens ~+10 %, verliert bis −100 %, wenn sich der Kurs verdoppelt. Die frühere Annahme („R × Abstand zum Referenzkurs“, Kauf zum Brief immer ≈ −90 %) war falsch. Der Leitzins wird zweimal gesetzt: ~2 min vor Schluss (Fenster ohne den ältesten Tender, nur 6 Tage) und ~1 min nach der Zuteilung (7 Tage) – nur der zweite Wert zählt. Bieter: nur Banken (Forum 2022), höchstens der Kreditrahmen – er begrenzt den **Kaufpreis**, nicht den Nennwert (Stockbrot, Rahmen 800 Bio. €: 8,001 Bio. Stk. zu 98 %, 7,843 Bio. zu 102 % = 799,999 Bio. €; `maxBidShares(rahmen, preis)`). Stand 09/2026: Stockbrot Bank ~97 % der Stücke und wechselt zwischen 98 und 102 %, der Rest bietet 102 %. **Unbestätigt:** ob wirklich jedes Gebot voll zugeteilt wird (bisher ja), ob Nicht-Banken abgewiesen werden und wie genau das Limit rechnet – Bieten/Zurückziehen/Kredit sind nur mit abgefangenen Requests geprüft.
  - **Systemanleihen:** `POST /api/systembonds?companyId&numberOfBonds` = Kredit **aufnehmen** (die Bank gibt Anleihen aus, die Zentralbank kauft sie zum Systemanleihe-Zins) – kaufen können Spieler sie nicht (kein Brief, laufende Systemanleihen ohne Geld/Brief). Nennwert 100 €.
  - `maxCentralBankLoans` = 10 % der Einlage; `takenCentralBankLoans` ist bei fast allen Banken 0. Systemanleihen nennen keinen Emittenten. `centralbankreserves` liest nur der CEO; Einlage anderer Banken über `companyprofiles` (`reserves`) oder die Highscore `RESERVES`.
  - **Performance/Einstand:** Positionen aus `/api/v2/my/portfolio` bzw. `/api/portfolios/{id}` tragen `averageBuyingPrice` schon – identisch mit `GET /api/v2/averagebuyingprice?securitiesAccountId=&securityIdentifier=` (liefert nur die nackte Zahl). Also **keine** Abfrage je Position. `0` = kein Kaufpreis (geschürft, emittiert, geschenkt) → kein Buchgewinn. Buchgewinn wie `PositionTable`: zum Geld (sonst letzter Kurs), Anleihen/Repos über `volume × (1 − Einstand/Kurs)` (`positionResult`).
  - **Trade-Statistik** `/api/v2/trades/stats/summary|best|worst|wins|losses` (`securitiesAccountId`, `startDate`, `endDate`, `securityIdentifier`): antwortet für **jedes** Konto, nicht nur eigene. `wins`/`losses` sind Seiten von `TradeWinView` (neueste zuerst), `sort=profitLoss,desc|asc` geht. `best`/`worst` ohne Trades → 200 mit leerem Body. `winRate` in Prozent (81,46). Verkäufe von Anleihen ohne Einstand (selbst emittiert, `averageBuyingPrice` 0) zählen mit Kurs-% × Stück als Gewinn (z. B. „+2,25 Bio. €“, 100 %) – verzerrt Summe und „bester Trade“ bei Emittenten.
  - `GET /api/v2/sharepositions?securityIdentifier=` (Pflicht) = meine Positionen in diesem Papier über **alle meine Konten** (privat + geführte Firmen) mit `averageBuyingPrice`, ohne Anteile in Orders; fremde Konten → `[]`. Genutzt in der Order-Maske der Wertpapierseite für Firmenkonten (nur wenn man CEO ist). Ohne ASIN → 400.
  - `useOrderbook`/`usePriceSpread` brauchen `enabled: !!asin` (sonst `/api/orderbook/` → 500, solange die ASIN noch lädt).
  - Screenshots öffnen Seiten wirklich: ein geöffneter Chat wird als gelesen markiert (`PUT /api/v2/my/chats/read`).
  - **Suche in Beiträgen:** `GET /api/v2/posts/search?q=&boardId=&includeComments=` findet nur **Forenbeiträge** (auch Firmen-Foren), keine Zeitungsartikel. Ganze Wörter, ohne Groß/Klein, ohne Präfix/Stamm („Leitz“ → 0, „Anleihe“ ≠ „Anleihen“), mehrere Wörter = alle; Reihenfolge nach Relevanz (das `sort` in der Antwort ist Deko). `includeComments` ist standardmäßig an (Antworten: `comment: true`, Thema in `root`); `boardId` gilt nur für genau dieses Board, nicht für Unterforen. Jeder Treffer hat `messageBoard`. Die Zeitung sucht mit `GET /api/v2/news?search=` (Teilwort in Titel und Text), das Board mit `/messageboards/{id}/posts?search=`.
  - **Hilfetexte:** `GET /api/v2/helpcomments?identifier=&locale=de` → `{ text }`, für unbekannte Kennungen 200 mit „Es gibt keine Hilfe für diese Kennung“. Es gibt keine Liste; per Feldnamen der Spec gefunden (18): `alphaCoins asin averageBondInterestRate centralBankReserves counterParty faceValue freeFloatInPercent hourlyChange limitOrder listingType mainInterestRate marketCap marketOrder maxCentralBankLoans netCash privateCash spread systemBond`. Texte siezen und haben Tippfehler → `helpText()`. Laut `mainInterestRate`: Leitzins = volumengewichtet aus den Geboten der **letzten sieben Tage** (nicht 30) – stimmt, siehe **Zinstender**.
  - Der Server drosselt: ~900 schnelle GETs in Folge (4 parallel) → `429`. Massenabfragen langsam und nacheinander.
  - **Chat verwalten:** Umbenennen `PUT /api/v2/chats/{chatId}?chatName=` – der Endpunkt nimmt auch `readonly`/`public`, deshalb beide unverändert mitsenden. Mitglied entfernen `DELETE /api/v2/chatmemberships/{membershipId}` (ID der Mitgliedschaft aus `chatmemberships?chatId=`, nicht die Nutzer-ID; `/api/chats/removeuser` ist alt). Rollen `OWNER > DEPUTY > MODERATOR > AUTHOR > READER`; angeboten nur in Gruppen für Inhaber/Stellvertretung gegen niedrigere Rollen (`canRemoveMember`) – beides **ungetestet gegen den Server** (nur mit abgefangenen Requests im Browser geprüft). `GET /api/v2/my/chats/unread/count` = Zahl der **Chats** mit Ungelesenem (Spec, am 25.09.2026 geprüft: 1 = `unreadSummary().chats`); die App zählt selbst aus `/my/chats` und zeigt die Zahl der **Nachrichten** (`useChatUnread().messages`), kein zweiter Abruf nötig. Lobbys haben immer `numOfUnreadMessages: 0`. Der alte Zähler im Kopf (`bnk-hdr__badge`, dunkler Kasten) fiel nicht auf – seit DS-Version 56 ein helles Schild wie an der Glocke.
  - **Unternehmensdaten:** `GET /api/v2/companycaps/{companyId}` = der Block `companyCapabilities` aus `companyprofiles` (+ `designatedSponsor`) – kein eigener Hook nötig. `GET /api/v2/companyhistograms/{companyId}` = **Verteilungen über alle Unternehmen**, keine Zeitreihe: je Kennzahl (`bookValue`, `netCash`, `cash`, `cashFlow`, `tradeVolume`, `outstandingShares`, `sharesIn(Buys|Sells)`, `(bonds|repos|systemRepos)Volume`, `centralBankReserves`, `closePrice`) 20 log-Klassen `"[lo,hi]" → Anzahl`, `highlightValue` (Wert des Unternehmens = letzter Tagesabschluss aus `historizedcompanydata`, ~18:50, nicht der Live-Wert), `highlightRange` (seine Klasse), `decile` (1 = unterstes Zehntel). **Grundgesamtheit:** `bookValue`, `netCash`, `cash`, `cashFlow`, `(bonds|repos|systemRepos)Volume`, `centralBankReserves` zählen ~9.500 Unternehmen; `tradeVolume`, `outstandingShares`, `sharesIn(Buys|Sells)` (und `closePrice`) zählen **alle ~200.000 Wertpapiere** (Klasse [0,5] ≈ 100.000, [999,5622] ≈ 90.000 – Immobilien, Anleihen, Repos). Deshalb landete jede Aktie mit 50.000 Stück in den „oberen 10 %“ (tatsächlich: mehr als 96 % aller Wertpapiere, unter Unternehmen etwa Mitte). `decile` = ⌊Anteil echt darunter × 10⌋ + 1 aus den genauen Werten – liegt bei allen geprüften Firmen (Alphakasse, lalaland72, Aykoc, georgysorosi96, Prime Reserve Bank) innerhalb der eigenen Klasse, ist also nicht falsch, aber bei Gleichstand irreführend (Cashflow 0: 77 % gleichauf → Dezil 1 = „untere 10 %“). Wir rechnen selbst (`standing()` in `profile.ts`): Anteil darunter / in der Klasse / darüber, Position = Mitte von Klasse ∩ Dezil, ab 25 % in der Klasse „gleichauf mit …“; Text nennt die Grundgesamtheit („mehr als 96 % aller Wertpapiere“). Diagramm: Anteil je Klasse linear in %, darunter blass, eigene Klasse voll, Markierungslinie, Achse an den Klassengrenzen (2 Stellen). `bondsVolume` = Anleihen **im Depot** (Alphakasse 17,8 Bio. bei `issuedBonds: []`), `repos`/`systemReposVolume` netto, negativ = Verpflichtung (Alphakasse −2,5 Bio. = genutzter Zentralbankkredit). Anzahlen je Kennzahl verschieden. `closePrice` lassen wir weg (Klassen bis −100, alle Wertpapiere). `/api/v2/my/companyhistograms` = dasselbe paginiert für die eigenen Unternehmen (Testkonto führt keins → leer, nicht eingebaut). Seite `/unternehmen/:asin?ansicht=einordnung&kennzahl=bookValue` (`src/companies/profile.ts`, `ProfileViews.tsx`).

Empfänger jedes Spielers/Unternehmens: `GET /api/v2/securitiesaccountdetails?search=` → `clearingAccountId` = Bankkonto (geprüft: eigenes Privatdepot → eigenes Bankkonto). Der alte Fehler: das DS-`TransferForm` kennt nur eigene Konten, ohne Firma gab es gar kein Formular. Absender ist **nur das Privatkonto** – von Firmenkonten nimmt der Server keine Überweisungen an (Nutzer bestätigt, 27.09.2026); die Konten der CEO-Firmen (`/api/companies/ceo/userid/{id}`) sind nur Empfänger (`private` in `bankAccounts`, auf `/bank` ist die gezeigte Firma als Empfänger vorgewählt). Ob der Server Überweisungen an fremde Konten annimmt, ist **ungetestet** (nur mit abgefangenem fetch geprüft; im Live-Log gibt es „Private bank transfer“ zwischen fremden Konten). `GET /api/v2/cashtransferlogs/{id}` liest **jedes** Konto (auch fremde), `size=1000` geht (Alphakasse ≈ 1 Tag, ~7.900 insgesamt); `GET /api/cashtransferlogs?startDate=` ohne Konto = die letzten 1.000 Buchungen des ganzen Spiels. Vorlagen (`categorize`/`describe` in `src/me/bank.ts`): `# shares of # (#)` (Handel), `Repurchase of # (#): # bonds`, `Salary from # (#)`, `Central bank reserves interest payment: #`, `Central Bank Reserves increased`, `Private bank transfer`, `Warrant Deposit|refund`, Fonds-/Index-Gebühren, `Payment for merger of # (#) into # (#)`, `Liquidation of # (#)`, `Founding a new company called #`; Dividenden-/Anleihezins-Vorlagen noch nicht gesehen (Stichwort-Regel). Laufender Saldo = aktueller Stand minus alle späteren Buchungen – der Stand muss **gleichzeitig** gelesen werden (`useCashLedger` holt `/api/v2/bankaccounts/{id}` mit), sonst läuft die Linie bei Firmen mit Bio.-Repos ins Minus. Kontoname der Gegenseite ist nicht abfragbar (nur eigene Konten bekommen Namen).

Texte als `MessagePrototype` (Vorlagen in `messages.ts`, Logo-Wechsel enthalten Bild-URLs – die Übersetzung lässt sie weg). `size=500` geht; der Filter `historyType` antwortet 500. Unbekannte ID → 200 mit leerer Liste. `/unternehmen/:asin?ansicht=chronik`. Für Spieler (`/spieler/:name`, ~400 Einträge bei aktiven CEOs) noch nicht eingebaut.
  - **Trade-Log des Markts** (`GET /api/securityorderlogs`, Seite `/stroeme`): höchstens **1.000 Trades je Abruf**, neueste zuerst; `page`/`size` werden ignoriert. Weiter zurück mit `startDate` + `endDate` = ältester gesehener Trade (inklusiv, IDs entdoppeln, `collectPages`). Der Markt hat ~100–170 Trades/min: 1 Std. ≈ 6.000 Trades = 7 Abrufe (~2,5 s, je ~425 KB), 3 Std. ≈ 20 Abrufe, 12 Std. ≈ 70–80 Abrufe (~30 MB, lädt nacheinander, danach nur Neues); 24 Std. wären ~130 Abrufe – nicht angeboten. Filter `buyerSecuritiesAccountId`/`sellerSecuritiesAccountId` gehen für **jedes** Konto (je 1.000, reicht bei kleinen Konten Tage zurück). `volume` ist € (Anleihen: Kurs % × Nennwert 100). **Namen:** Firmenkonten tragen den Firmennamen, Privatkonten einen **leeren** Namen → `GET /api/v2/securitiesaccountdetails/{id}` (Privat: Spielername; Firma: „Name (ASIN) | CEO“; ETF-Fonds: `privateAccount: true` mit Namen `ef-sec-acc-<uuid>`, zeigen wir als „ETF-Fonds xxxx“; `/api/v2/etfs` ohne ASIN → 500). Wir lösen nur die ~25 größten + ~25 aktivsten Konten auf (je 2 gleichzeitig, für die Sitzung gecacht). Beobachtet (25.09.2026): nach € sind ~98 % Anleihen (Alpha-Bank-Tenderanleihe 0 % an Privatdepots), nach Zahl ~93 % Aktien; ETF-Fonds kaufen Aktien in Einzeltrades zu Mrd. €. Trades zu ≤ 0,01 € sind Übertragungen (~5 %, v. a. AlphaCoins an sich selbst) und zählen nie als Umsatz. `/api/marketstatistics` = 2.400 Stundenschnappschüsse (3 MB) – nicht genutzt.
  - Geldflüsse – Namen: Privatdepots haben im Log keinen Namen. Nachgeschlagen (`/api/v2/securitiesaccountdetails/{id}`, je Sitzung gecacht, 2 parallel) werden die größten/aktivsten Konten (`accountsToResolve`) **plus** jedes Privatdepot, das Geldfluss, Paare, Netto oder Auffällig zeigen (`shownPrivateAccounts`); angezeigt als „Name (privat)“ (`labelOf`), damit man es nicht mit einer Firma derselben Person verwechselt.
  - Chat ohne Layout-Sprung: Untertitel immer gesetzt (`' '`), beim Weiterleiten auf den neuesten Chat hält ein deaktivierter `ChatComposer` den Platz, die Regel für öffentliche Chats steht im Platzhalter des Eingabefelds statt als `notice`-Banner (der kam erst mit der Chatliste und schob den Verlauf ~60 px).
